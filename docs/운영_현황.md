# 자비스 운영 및 검증 현황

이 프로젝트는 Sasarisa를 참고한 Windows 구현입니다. 원본과 기능이 동일하다는 검증은 아직 이루어지지 않았습니다.

## 안전 관련 동작

- 카카오톡은 대화방의 빈 입력란을 선택한 상태에서 요청해야 합니다. 실제 대화방 이름·프로세스·입력란을 확인한 뒤 별도 확인을 받습니다. 빈 입력란의 안내 문구가 실제 내용으로 반환되는 문제를 보완하고, 앱 입력 이벤트가 발생하도록 Windows 키보드 입력 경로를 추가했습니다. 접근성 전송 버튼이 없는 경우 같은 입력란의 포커스를 재검사한 뒤 전송 키를 사용합니다. 입력란이 비워지는 것과 상대방 수신은 별개이며, 결과가 불명확할 때 자동 재전송하지 않습니다.
- 창 자동 닫기와 음량 외 작업의 자동 되돌리기는 지원하지 않습니다.
- 로컬 서버는 같은 출처의 브라우저 요청만 허용합니다. 인증된 사용자 계정이나 로컬 프로세스 간 권한 분리는 제공하지 않습니다.
- 타이머는 서버가 실행 중일 때 만료 이벤트를 생성하고 열린 HUD 또는 웹 화면이 이를 표시합니다. 음성 출력은 해당 장치와 음성 엔진의 정상 작동에 의존합니다. 서버와 화면이 모두 닫혀 있을 때에는 알림을 받을 수 없습니다.
- 2026-10-28 실제 Windows 환경에서 한국어 `Microsoft Heami` 음성으로 HUD 시간 안내가 스피커에서 들리는 것을 사용자가 확인했습니다. 마이크로 말한 호출어와 시간 질문도 서버에서 인식했습니다. Edge Neural 음성 연결은 별도로 검증하지 않았습니다.
- 온라인 음성 생성 실패 시 서버는 Windows 한국어 음성으로 WAV를 생성합니다. HUD는 실제 WAV 헤더와 MP3 형식을 구분해 재생하며, 재생 완료 후 마이크 음소거를 해제합니다. 서버 오디오가 없거나 재생에 실패하면 HUD 자체의 Windows 음성 합성으로 한 번 더 시도합니다. 실패를 조용히 무시하지 않고 HUD에 표시합니다.
- 코덱스 코딩 작업은 `코덱스한테 ...`라고 요청한 뒤 확인하면 시작합니다. 기본 작업 폴더는 이 프로젝트이며 `config.json`의 `codingWorkspace`로 변경할 수 있습니다. AI 사용량의 실제 토큰 수는 측정하지 않습니다.

## 글과 메일

- 일반 입력창에 포커스를 둔 상태에서 `자비스 받아쓰기`라고 말한 뒤 이어서 말씀하면 인식된 문장이 입력창 끝에 추가됩니다. `그만`으로 종료합니다. 앱이 Windows 접근성 `ValuePattern`을 지원해야 하고, 중간에 입력 내용이 바뀌면 중단합니다.
- 글을 선택하고 `자비스 존댓말로 바꿔`라고 말하면 로컬 Ollama가 수정안을 만듭니다. 확인하면 선택 내용이 바뀝니다. 앱의 Windows 접근성 선택 기능과 로컬 모델이 필요합니다.
- 메일 내용의 텍스트를 선택한 채 `자비스 선택한 메일 읽어` 또는 `자비스 선택한 메일 답장 써줘`라고 말할 수 있습니다. 답장 초안을 만든 뒤 빈 답장란을 선택하고 `자비스 메일 답장 입력해`라고 말하면 초안을 입력합니다. 메일 전송은 직접 확인해 수행해야 하며, 실제 메일 서비스와의 연동은 아직 실환경 검증하지 않았습니다.
- 대상 앱에 포커스가 있어야 하므로 HUD 텍스트 입력란에 입력하는 대신 대상 입력창을 선택한 채 음성으로 요청해야 합니다. 터미널·코드 편집기·암호 입력란은 자동 입력 대상에서 제외합니다.
- 2026-10-28 Gmail 브라우저에서 본인 계정으로 보낼 시험 초안을 작성했습니다. 이후 Chrome 연결 중단으로 Gmail 연결 도구를 사용해 승인받은 시험 메일을 보내고 받은편지함의 같은 메시지 ID·제목·본문을 확인했습니다. 이는 Gmail 계정의 송수신 확인이며 자비스 프로그램의 자동 메일 전송 기능 검증은 아닙니다. 프로그램은 현재 선택한 메일 읽기·답장 초안 작성·입력 기능을 제공하며 자동 메일 전송 연동은 완료되지 않았습니다.

## 음성이 중간에서 실행되던 문제

- 브라우저 음성 인식의 `isFinal`을 곧바로 명령 실행으로 처리하던 경로를 수정했습니다. 이제 확정된 조각을 합치고, 인식 결과 변경과 감지된 발화가 모두 약 2초간 멈춘 뒤 하나의 명령으로 넘깁니다. 미확정 중간 결과는 실행하지 않습니다.
- 미확정 결과가 계속 남으면 침묵 후 브라우저 인식 엔진에 확정을 요청합니다. 엔진이 확정하지 못하거나 응답하지 않으면 HUD에 다시 말하거나 입력하라는 안내를 표시하고 인식기를 재시작합니다. 문장 조각을 임의로 실행하지 않습니다. 지속적인 소음으로 실행 대기가 끝나지 않는 경우도 시간 제한 후 안내로 전환합니다.
- 명령 실행 오류도 최종 HUD 상태로 전달합니다. 입력창 확인 실패 등의 오류가 생긴 뒤 이전의 `받아 적는 중` 화면만 남던 경로를 보완했습니다. 같은 문장의 상태만 바뀌어도 HUD가 갱신되도록 표시 중복 판정에 상태 문구를 포함했습니다.
- HUD의 Windows 받아쓰기 입력란에서 1.35초 후 자동 실행하던 타이머를 제거했습니다. 이 입력란에서는 끝까지 말한 후 Enter 또는 전송 버튼을 눌러야 합니다. 호출어를 사용하는 상시 마이크는 위의 문장 합치기 방식으로 동작합니다.
- 실제 마이크에서 `자비스, 지금 시간을 알려줘`를 중간에 약 1초 쉬어 말한 시험은 호출어·시간·끝말이 포함된 하나의 최종 시간 명령으로 확인됐습니다. 모든 문장과 소음 환경에서의 인식 품질을 보장하지는 않습니다.

## 실행과 검증

- 2026-10-28 음악 제어 수정 후 실제 앱 API에서 유튜브 열기 → Windows `Playing`, 호출어 없이 `음악 꺼줘` → `Paused`, 같은 정지 명령 반복 → 계속 `Paused`, 다시 재생 → `Playing`, 새 이어 듣기 세션의 `꺼줘` → `Paused`를 확인했습니다. 결과는 `data/media-live-verification.json`에 저장했습니다. 이 검사는 음성 인식이 끝난 뒤의 실제 제어 경로를 사용하며, 사람의 마이크 발화 검증과 구분합니다.
- 음악 정지는 먼저 Windows 미디어 세션을 제어하고 실제 상태를 검사합니다. 실패하면 유튜브 접근성 제어로 재시도합니다. 영상·브라우저를 강제로 종료하지 않습니다. 대상이 없거나 상태 확인에 실패하면 완료로 표시하지 않습니다. `꺼줘`는 자비스가 연 음악 문맥이 있을 때 정지로 처리하고, 일반적인 다른 명령은 호출어 규칙을 유지합니다.
- 전용 음악 브라우저의 실행과 창 확인을 분리했습니다. 이 PC에서 Node 보조 프로세스 안의 CIM 조회가 멈추는 현상을 확인하여 Windows PowerShell 5.1의 WMI 조회로 변경했습니다. 브라우저 실행 여부는 실제 창 핸들로 확인합니다.
- 실행 서버는 `server.verified.js`, 명령 엔진은 `scripts/butler-engine.verified.js`입니다. `scripts/Freeze-VerifiedRuntime.js`는 검토한 소스를 명시적으로 승격하고 `data/verified-runtime.json`에 해시를 기록합니다. 일반 시작 과정에서는 파일을 덮어쓰거나 예전 scratch HUD를 가져오지 않습니다. `GET /api/status`의 `runtime`으로 실행 파일과 프로세스를 확인할 수 있습니다.
- 마이크 작업자는 `endpoint-media-v4`입니다. 전용 Chrome 프로필의 Web Lock으로 동시에 음성 인식을 시작하는 작업자를 한 개로 제한합니다. HUD는 5초마다 상태를 확인하고, 서버가 시작된 지 8초 이상 지났고 마이크 보고가 없거나 20초 이상 끊겼을 때 자비스 전용 마이크 프로세스만 다시 시작합니다. 재시도 간격은 최소 30초이며, 최신 보고가 있는 권한·장치 오류에는 재시작을 반복하지 않습니다. 기존 작업자 창 3개를 실제로 1개로 복구하고 마이크 `ready`, 음성 인식 `listening`을 확인했습니다.
- 최종 실행 HUD는 Windows 창 목록에서 주 모니터·항상 위·표시 창 1개를 확인했고, 실제 화면에서 입력란과 음악 정지 결과가 표시되는 것을 확인했습니다. `scripts/Check-HudWindows.ps1`는 이 조건들을 함께 검사합니다. `scripts/Verify-HudStartup.ps1`는 실행 중인 HUD를 읽기 검사하며, 꺼져 있을 때 `-StartIfStopped`를 지정해야 설치본을 실행해 부트 순서를 관찰합니다.

- 처음 앱을 실행하면 Windows 주 모니터에 부트 화면을 약 4초 표시하고 닫은 뒤, 같은 주 모니터에 입력란·전송 버튼이 있는 HUD 하나를 표시합니다. 부트 화면의 `HUD 시작` 버튼이나 Esc로 먼저 넘어갈 수 있습니다. 부트 화면이 떠 있는 동안 HUD는 숨겨져 있습니다.
- HUD는 모니터 수와 관계없이 주 모니터에 하나만 표시합니다. 보조·세 번째 모니터용 창 생성과 상태 복사 코드를 제거했습니다. 주 모니터가 바뀌면 같은 창을 새 주 모니터의 작업 영역 안으로 보정합니다. 주 모니터 안에서 위치를 조절할 수 있으며, 다른 모니터로 넘어가면 주 모니터 안으로 보정됩니다.
- 앱이 시작되기 전에 발생한 음성·인사 명령을 다시 실행하지 않습니다. 이전 인사 명령 때문에 부트 화면이 다시 열리던 문제를 보완했습니다.
- 부트 화면 먼저 표시, 부트·HUD 겹침 없음, 양쪽 모두 주 모니터 사용, 최종 HUD 1개·부트 화면 0개를 실제로 확인했습니다. `scripts/Verify-HudStartup.ps1`의 기존 강제 종료·준비 빌드 덮어쓰기 동작은 제거했습니다. 실행 파일 교체는 `scripts/Install-VerifiedRuntime.ps1`에서만 수행합니다.
- 바탕화면 아이콘을 두 번 더 실행한 후 Windows 창 목록을 검사해 프로세스 1개·표시되는 HUD 1개를 확인했습니다. `scripts/Check-HudWindows.ps1`로 같은 검사를 실행할 수 있습니다.
- 바탕화면의 `자비스 HUD` 아이콘과 `Start_자비스.cmd`는 프로젝트의 실행 스크립트를 통해 HUD를 엽니다. 실행 중인 정식 또는 갱신 중 HUD가 있으면 중복 실행하지 않습니다. 실제 Windows 바탕화면 폴더(OneDrive 경로 포함)를 사용합니다.
- HUD 내부에서도 단일 실행을 검사합니다. 실제 실행 파일을 두 번 실행했을 때 두 번째 프로세스가 종료되는 것을 확인했습니다. 마이크 시작과 HUD 유지 타이머는 HUD의 UI 스레드에서 시작합니다.
- 실행 아이콘과 CMD·BAT·VBS 시작 파일은 `scripts/Open-JarvisHud.ps1`를 통해 `bin/JarvisHud.exe`를 실행합니다. 정본 소스는 `scripts/JarvisMonitorOverlay.cs`이며, `scripts/verified-hud/MonitorOverlayApp.cs`는 빌드 시 생성하는 검증 사본입니다.
- `scripts/Build-VerifiedHud.ps1`는 정본을 `bin/JarvisHud.next.exe`로 빌드하고 소스·바이너리 해시를 기록합니다. 실행 중인 파일은 덮어쓰지 않습니다. 설치기는 해시를 검사하고 감시를 중지한 뒤 기존 프로세스의 종료를 기다려 교체합니다.
- `npm run test:speech`는 문장 조각 합치기, 발화 중 실행 보류, 확정 요청, 확정 실패·시간 초과 안내 및 중복 방지를 검사합니다. 실제 음성 클라이언트 콜백을 모의 인식 엔진과 함께 실행하는 회귀 검사도 포함합니다. 모의 검사는 실제 마이크 발화 검증과 구분해야 합니다.
- `npm run verify`는 임시 데이터 복사본에서 기존 명령 검사 13개를 실행합니다.
- `npm test`는 임시 데이터와 시작프로그램 폴더를 사용하여 로컬 API의 요청 제한, 메시지 처리, 타이머 이벤트, 시작프로그램 등록 및 해제를 확인합니다. 로컬 네트워크 연결이 허용되어야 합니다.
- 별도 시험 입력창에서 받아쓰기 입력과 로컬 모델을 이용한 글 수정 및 확인 후 교체를 실험했습니다. 격리된 임시 폴더에서 실제 Codex가 시험 파일을 만드는 것도 확인했습니다. 이 시험은 카카오톡이나 실제 메일 서비스에서의 동작을 보장하지 않습니다.
- `npm run rea`는 포함된 원본을 정적으로 스캔하고 보고서를 생성합니다. 보고서의 대응 관계는 구현 동등성의 증거가 아닙니다.
- 음성 라이브러리는 `package.json`에 선언되어 있습니다. 현재 구현은 별도 외부 경로에 설치된 모듈이나 AI 허브도 선택적으로 참조하므로 다른 PC에서 전체 동작이 보장되지는 않습니다.

## 2026-10-30 음성 연결과 긴 발화 보완

- 이전 실행본을 2분 관찰했을 때 물리 마이크 상태는 계속 `ready`였고 인식기만 약 0.2초 동안 `starting`으로 바뀌었습니다. 새 이벤트 기록에서 재발 원인은 무음 인식 종료인 `no-speech`로 확인됐습니다. `/api/ear/health`는 연결 여부를 그대로 보고하면서 마이크 상태·인식기 상태·종료 사유·보고 지연을 함께 제공합니다. 정상 재연결을 작업자 장애로 숨기거나 강제 재시작하지 않습니다.
- `endpoint-media-v5`는 실제 발화 활동을 문장 버퍼에 전달합니다. 결과가 10초간 바뀌지 않았다는 이유만으로 말하는 중에 인식기를 중지하던 조건을 제거했습니다. 설정된 침묵 시간(현재 3.8초) 뒤에 최종 문장을 실행합니다. 음악만으로 발화 시간이 늘어나지 않도록 인식기가 확인한 발화 활동을 사용합니다.
- HUD가 `음성 확정 실패` 문장을 일반 명령으로 다시 보내던 경로를 제거했습니다. 확정되지 않은 내용을 실행하지 않으며, 인식 세션 사이에는 이미 확정된 문장 조각을 유지합니다. 서버나 인식기가 받지 못한 음성을 복원하는 기능은 아닙니다.
- 중복 마이크 스트림 요청을 방지했고, HUD의 음성 결과 조회가 겹쳐 오래된 결과를 뒤늦게 표시하지 않도록 했습니다. 새 로그는 `data/speech-events-YYYY-MM-DD.jsonl`, 최근 이벤트 조회는 `/api/ear/events`입니다. 이 로그는 원문 음성이나 대화 내용을 저장하지 않고 상태·원인·시간·명령 종류를 기록합니다.
- 자동 검사에서는 2분간 발화 활동 유지, 실제 클라이언트의 45초 발화 중 강제 확정 방지, 인식 세션 사이 조각 유지, 미확정 실행 차단, 단일 마이크 요청을 통과했습니다. 사람의 실제 마이크 발화·명령 실행·스피커 확인 결과는 별도 실측 기록으로 구분합니다.
- 수정본의 12:45:38~12:50:40 KST HUD 관찰은 302.1초, 60개 표본 모두 통과했습니다. HUD PID 57188이 유지됐고 주 모니터·항상 위·창 한 개·응답성 조건 실패는 없었습니다. 음성 인식의 짧은 재연결 표본은 2개였습니다. 실제 사람의 긴 발화·명령 실행·스피커 확인은 사용자 시험 발화 대기 상태이며 완료로 처리하지 않았습니다. 진행 기록은 `data/verification/2026-10-30-speech-continuity.json`입니다.
- 이벤트의 의미는 [Web Speech API의 인식 이벤트 정의](https://webaudio.github.io/web-speech-api/#speechreco-events)를 참고했습니다. `end`는 인식 서비스 세션 종료이며 물리 마이크 장치 고장과 동일하지 않습니다.
